# MinIO 相关图片问答展示设计

日期：2026-08-20

## 目标

用户上传包含图片的 Markdown、PDF 或 DOCX 文档后，掌柜智库在回答相关问题时，能够把召回内容中的相关图片展示在聊天界面中。图片可以统一展示在答案正文下方；刷新页面或重新打开同一会话时，图片仍然保留。

## 已确认的根因

1. 部分已入库切片仍保存 `images/xxx.jpg` 相对路径，而查询节点只返回以 `http` 开头的图片 URL，因此这些图片在答案阶段被过滤。
2. 导入节点虽然会生成 MinIO URL，但切分节点曾经重新从磁盘读取原始 Markdown，导致替换后的 URL 没有进入 Milvus 切片。
3. 历史记录接口没有把 MongoDB 中已有的 `image_urls` 字段返回给前端。
4. MinIO URL 由字符串直接拼接，未统一处理 endpoint 是否已经包含协议，也未在返回前验证对象是否可访问。

## 设计方案

### 1. 导入链路

导入时保留现有图片摘要流程：读取图片、调用视觉模型生成摘要、上传原图到 MinIO。图片对象使用“图片目录 + 文档名”隔离，避免多个文档互相删除图片。

导入节点将 Markdown 和 HTML 两种图片语法统一替换为带 MinIO URL 的 Markdown 图片语法。切分节点优先使用工作流状态中的替换后 `md_content`，确保摘要和 URL 进入切片并最终写入 Milvus。

### 2. 查询链路

答案生成节点从最终召回切片提取图片 URL，并对旧数据中的相对路径提供兼容转换：如果召回内容仍是 `images/xxx.jpg`，则根据文档名拼接当前 MinIO 对象 URL。转换后的 URL 去重后写入：

- SSE `final` 事件的 `image_urls`；
- MongoDB assistant 历史记录的 `image_urls`。

最终事件同时携带 `answer` 与 `image_urls`，避免前端依赖流式文本作为答案兜底。

### 3. 历史记录与前端

历史接口原样返回 `image_urls`，前端历史消息和实时消息统一经过图片渲染函数处理。图片展示在答案文本下方，并保留可点击的原始 URL；图片加载失败时不影响文字答案显示，同时记录可定位的前端错误信息。

### 4. URL 与错误处理

统一生成 MinIO 对象 URL：

- endpoint 已带 `http://` 或 `https://` 时不重复添加协议；
- endpoint 为 `host:port` 时按当前 MinIO 客户端的非 TLS 配置补充 `http://`；
- 图片文件名进行 URL 编码，避免中文、空格和特殊字符导致 `<img>` 加载失败。

导入、查询和历史返回处增加轻量日志，分别记录图片发现数、提取数和返回数，不记录图片二进制或密钥。

## 兼容性与数据要求

代码兼容旧切片中的相对图片路径，但旧对象如果已经被旧版“全目录删除”逻辑清理，则无法凭空恢复。修复后建议重新导入一次原始文档，以生成稳定的文档隔离对象和 MinIO URL。

不修改用户原始 Inbox 或上传原图；只修改工作流生成的备份 Markdown、查询返回结构和前端渲染逻辑。

## 验收标准

1. 新导入一份带图片的文档，MinIO 中能看到图片对象。
2. 查询与图片上下文相关的问题时，SSE `final` 事件包含非空 `image_urls`。
3. 聊天界面能看到至少一张对应图片，图片下方有可点击 URL。
4. 刷新页面或重新打开同一会话，历史答案中的图片仍能显示。
5. 没有相关图片时，答案正常显示且不出现空图片容器。
6. 旧切片包含 `images/xxx.jpg` 时，查询不会因图片路径格式而崩溃。
7. 既有文本问答、导入流程和历史记录功能不受影响。

## 测试策略

- 使用纯函数测试验证 MinIO endpoint 规范化、图片 URL 提取、相对路径兼容转换和去重。
- 使用接口级测试验证 `/history` 返回 `image_urls`，SSE final 数据同时含答案和图片。
- 使用浏览器手动验证实时回答、刷新历史、图片加载失败三种界面场景。
- 修改完成后运行项目现有测试与 Python 编译检查，并记录无法执行的外部依赖验证项。
